roadstyle as a Rust library: the design and the migration plan

Status: agreed 2026-10-23: decisions 1 to 8 as recommended, decision 9 open. Nothing in this document is built. It continues One Rust engine for roadstyle (steps 1 and 3 are done) and uses The style in a config file and A general core: roads, items, and views. The decisions are in Decisions.

Summary

roadstyle has one reference implementation, in Python (version 0.24.3, about 11,000 lines of Python, a 1,688-line page template and about 500 tests). A Rust crate, roadstyle-rs (5,582 lines), already makes the style and the vector tiles of the simple mode, and it has the level solver. duckosm-rust's browser page and the GeoLibre plugin use it through WebAssembly. The rest of roadstyle is only in Python.

This plan makes one Rust library with a pure core and adapters around the core. The core has three independent parts: the road model, the look (the typed config) and the engine. The adapters read and write files and connect the core to Rust, JavaScript and Python. A typed render model (the drawing numbers of each road, the objects attached to roads and one order for the whole map) replaces the __rs_* properties that Python and Rust bake today. The plan has seven phases. Python roadstyle stays the reference until the last phase: a change in the Rust output is correct only when it is byte for byte equal to the output of Python.

Facts that the plan must use:

  • The engine reads one input file, look.json (63 KB). Python writes it (tools/make_spike_fixture.py of geolibre-roadstyle, mapstyle's render_map(_export=...)). It holds Python's internal tables: settings, args, theme, config, styles, roads_model, slots, features, interaction. It has no version and no schema.
  • The scope of the engine is the simple mode with stored levels (layers.rs:506): no 3D decks, no metre widths, no items, no full mode (simple=False).
  • Errors are Result<_, String> (about 25 places). There are no features, no threads and no benchmarks.
  • The golden tests compare SHA-256 hashes with the output of geolibre-roadstyle's port (commit 0806ac2, with building rule C). That port was compared with Python's output in geolibre-roadstyle (spike/test_compare.py). This repository has no golden test from Python yet. The branch rust-colors adds the first one (tests/make_goldens.py, not committed).
  • No CI job runs cargo.

The architecture

The choice: a pure core with adapters around it

The core has no I/O. It has three parts, and two of them are independent inputs of the third:

  • The road model (roadstyle-model): the roads as columns, their geometry, the column map, the validation.
  • The look (roadstyle-look): the typed, versioned config: palettes, profiles, settings and the map options that change the style.
  • The engine (roadstyle-engine, roadstyle-tiles, roadstyle-levels): pure functions from (roads, look) to the style, the tiles and the levels.

The adapters are around the core. Each one connects the core to one thing outside:

  • Readers and writers (roadstyle-io): GeoParquet, Arrow, GeoJSON, DuckDB, the style file, the tile folder, PMTiles, the HTML page.
  • Bindings: WebAssembly and JavaScript (roadstyle-wasm), Python (roadstyle-py).
  • The dashboard module (JavaScript): a separate front-end package. It reads only the style and its roadstyle:* metadata. It does not call the engine.

The core in the middle has no arrow to a file, a database or a browser. The model and the look do not point at each other.

Rules of the layers

  1. A dependency points into the core, never out of it. roadstyle-engine does not know Parquet, Python or JavaScript.
  2. roadstyle-model and roadstyle-look do not depend on each other. Data-driven color needs both the values of a column and the look, so it is a function of the engine, not of the look.
  3. The core builds for wasm32-unknown-unknown with no features. A CI job checks this (see Quality).
  4. The engine is single-thread by default. The feature parallel adds rayon for the native build.
  5. The page options (popups, Street View, controls) do not go into the engine. The engine copies the few that the style must carry into its metadata (roadstyle:interaction). The other options go to the dashboard module.
  6. One copy of each rule. The worker SQL, the palettes and the profiles each have one file, and each user takes them from one commit of this repository.

The alternatives that I did not choose

Alternative Why not
A strict stack: data, then config, then engine, then interface (each layer uses only the layer under it) The config does not need the data, and the data does not need the config. A stack makes one depend on the other with no reason. It also puts the readers (Parquet, DuckDB) under the engine, so the WebAssembly build carries them.
One crate with modules and feature flags (today's roadstyle-rs) It works for one user. With three users it has costs: duckosm-core takes Parquet and Arrow to get only the level solver; a change in one module rebuilds all; the public API is every pub item. The crate split is cheap now (5,600 lines) and expensive later.
Many small crates (one per module: slots, simple, overlays, ...) These modules change together for one style change. More crates give more version bumps and more Cargo.toml files, and no user needs them alone.
The engine builds the page (HTML) The page is interaction, not style. Three pages exist (the Python page, the duckosm-rust page, the GeoLibre plugin) and each has its own frame. The dashboard module serves all three. The page writer is a small adapter in roadstyle-io.
Keep look.json as Python's internal tables Each Python refactor can break the Rust users, and no test shows it. A typed, versioned look with a schema stops this.
A full rewrite of Python roadstyle in Rust at once No reference during the work, and 16 Python projects wait. Part by part, with Python as the reference, each part can ship alone.

Errors

Each crate has one error enum (thiserror), #[non_exhaustive]. The facade has roadstyle::Error, which holds each of them. Each error says what is wrong, where (a column, a key path, a feature id) and what to do.

Error Examples
DataError missing column highway; column layer has type List, expected integer or text; feature 812 has no line; 230,114 roads, the limit is 200,000
LookError roads.width.major: expected a map of zoom to px, found a number; unknown palette ambr (the names are amber, carto, highsat, mono); look version 3, this engine reads 1 and 2
EngineError a view names palette x that the look does not have
TileError zoom 23 is past the last zoom 16
IoError Parquet file is not readable; the DuckDB file has no visualization.edge_levels (give the rs.save_levels command)

In JavaScript, an error is a thrown Error with name = the kind (LookError) and a path property. In Python, each error is a subclass of ValueError (roadstyle.LookError(ValueError)), so except ValueError in user code still works.

The engine is the same code in both places. In the browser it runs in a worker, and the main thread only draws.

The steps:

  1. Input. Python gives an Arrow table (no copy from pyarrow). The browser gives the Parquet bytes that duckdb-wasm writes.
  2. Model. The reader maps the columns (ColumnMap: highway_col, edge_id_col, tunnel_col, ...), checks them and makes a RoadTable.
  3. Look. Look::resolve merges the palette, the profile and the settings, and adds the map options that change the style.
  4. Style. The engine makes the layers, the sources and the metadata.
  5. Output. Inline (the sources in the style, export_inline), tiled (Tiler, tiles on request), or files (export_style, the page).
  6. Page. MapLibre draws the style. The dashboard module reads the metadata and adds the controls.

The render model

The render model is the set of values that the engine draws from: the drawing numbers of each road, the objects that belong to a road, and the order of all layers of the map. It is the core of roadstyle, and today it has no type. Python bakes it as about 40 __rs_* properties (render_web.py), and the crate copies these properties (roads.rs, simple.rs, slots.rs). This section makes it one typed model in roadstyle-model, with the rules in roadstyle-engine. The specification of the numbers stays Divided casing and one band. This section does not change it.

The numbers and ends of a road: RoadDraw

RoadDraw holds one row for each edge, as columns:

Field Type Meaning Default
edge_id EdgeId (i64, or text for other schemas) the id of the edge required
class dictionary text, and is_link the road class (highway without _link) the fallback style
geometry a line in the coordinate buffer the edge's line required
levels Levels { casing_start, casing_main, casing_end, fill: i16 } the four positions see the rules below
ends [End; 2], End { head_m: Option<f32>, cap: Cap }, Cap = Round, Square, Flat the head length and the shape of each end head_m of the profile (5 m), Round

look access, width_m, the data-driven paint (task 1) the colors and widths of this edge none

The engine derives the pieces from RoadDraw with the rules of today: three casing parts (start head, main, end head), or two halves for a short road (one cut, short_road_heads.md), or one piece when the three numbers are equal; seams of 0.5 m and laps of 2 m at each cut; one casing for a two-way pair (twin_casing = "one"); fill halves when the two caps differ; bridge shadows; tunnel gap and dashes.

Where the numbers come from: LevelPlan

pub enum LevelPlan {
    Given(LevelColumns),                       // the caller's columns (casing_level_col, fill_level_col, ...)
    Stored { table: LevelColumns, meta: LevelMeta }, // visualization.edge_levels and edge_levels_meta
    Compute { method: Method, params: SolveParams, edits: Edits },  // Tags, or Solve with the rule rows
    Partial { given: LevelColumns, method: Method, params: SolveParams, edits: Edits }, // some roads given, the rest solved
}

The rules:

  1. One source of numbers for one map. The positions are a ranking for the whole network: a number of one road means something only against the numbers of the roads that it meets or crosses. Thus all numbers of one map come from one solve or one stored table (levels_split_casing.md, section 12.1). The engine does not mix two sources by a default.
  2. Some numbers given, the rest computed. The caller gives the numbers of some roads. These roads are held (fixed: all four numbers of a whole road), and the solver computes the others with them as bounds. Python has this as solve_levels(fixed=...) (the editor's local solve). It is the only way to mix: a road with no number is never drawn at 0 without a message.
  3. The ends are not the numbers. For each end, the first source that has a value wins: the user's edit (heads.csv, caps.csv), the caller's column (head_start_m_col, cap_start_col, ...), the solver's result (the square cap at the dead end of a two-way road, auto_ends when asked), the profile (head_m, round).
  4. Edits are rules, not numbers. An edit adds a row to the solver's input or switches one off (enabled = false removes the same row of pairs.csv). It never sets a number. The Rust solver has no edits today (levels/mod.rs:3), and P4 adds them.
  5. Stored numbers are checked. The engine compares the stored parameters (method, head_m, band_dist, margin, max_level, band_source, order_source, min_positions), the number of edges and the edge hash. An edge with no stored row is an error, as in Python's levels_db. (The worker SQL of today joins with LEFT JOIN, and a missing row becomes 0.)
  6. One normalization. A value that is not a number is an error with Given and Stored (Python reads it as 0 today: P0 lists this as a difference to decide). A float is rounded half to even. The main casing number is never above the fill, and each head is lowered to the fill. A reversed edge has its start and end swapped.
  7. The source is in the style. The metadata roadstyle:levels holds the method, the edge hash, the version and the pairs that the solver gave up, so a page can show where the numbers come from.

Objects that belong to a road: Attachment

Today four mechanisms put objects on roads: the slots (names and arrows), Overlay(edge_col=...), items= (metre-wide lines), and edge_attach (the base map's crossings and traffic signals, by distance). Each one carries its edge in its own way. edge_items.md asks for one mechanism. The model is one type:

pub struct Attachment {
    pub edge: EdgeId,     // the edge that it belongs to
    pub at: Along,        // Geometry(given) | Whole | At { m } | Span { from_m, to_m }: metres along the edge
    pub side: Side,       // Center | Right | Left, of the edge's direction
    pub offset_m: f32,    // from the side
    pub kind: Kind,       // Line | Fill | Circle | Icon | Text
    pub role: RoleId,     // a style of the profile: "lane", "divider", "sign", "sensor", "bus_stop"
    pub order: i16,       // inside the position: the lower is drawn first
    pub phase: Phase,     // OverFill (default) | WithCasing
    pub row: u32,         // the row of its data, for the popup
}
  • What it gets from its edge. The position (the edge's fill number), the tunnel look, the filters (hiding a road hides its objects) and the selection (a click selects the road too, unless the role says interactive: false). Every piece carries the same edge label (__rs_edge, and __rs_edge2 for both directions of a pair).
  • The place. Geometry is today's case: the caller gives the line, polygon or point. At, Span, Side and offset_m are new: the engine cuts the edge's line at the metres (linear referencing) and moves the result to the side. A sensor at 40 m on the right, a bus stop at the end, a lane marking from 10 m to 60 m need no geometry from the caller. An object on one lane of a two-way road follows the lane's offset in pixels (the expression of the road), not a fixed number of metres.
  • Built in. The slots are attachments that the engine makes: a name is Text on a Span (an even slot), an arrow is Icon on a Span (an odd slot). The base map's crossings and traffic signals become attachments when they are snapped to the edge that is drawn on top (edge_attach).
  • New kinds of objects need no change of the core. A new object is a new role: a style entry in a profile (its kind and its paint values) and a palette key for its color. The five kinds are a closed list in the core. A sixth kind is a change of the core and of the layer planner.
  • Errors. An edge id that is not among the roads is an error with the count and the first ids, as in Python today.

The rules:

  1. Layers are found by their role and group, not by their id. The ids change with the plan (roads-fill-lv3) and a host can add a prefix (duckosm-rust adds rs-, GeoLibre renames the layers). Today filter.js takes every layer whose id starts with roads.
  2. Public and internal. Public for a host: the metadata keys above, the layer roles and groups, the data columns (edge_id, the class column and every column kept in the tiles), and the anchor layer roads-highlight. Internal (between the engine and the dashboard of the same version, checked by a test): the __rs_* properties that the dashboard reads (__rs_edge, __rs_edge2, __rs_edges, __rs_cls, __rs_lvl, __rs_tunnel, __rs_bridge, __rs_access, __rs_k, __rs_fl, __rs_ord, __rs_arw, the slot fields), the feature ids, and the layer ids.
  3. The ids. A feature's id is its row in the table (the roads source), or the row times 24 plus the piece (the simple source), because feature state needs small numbers. The public API takes the edge id (edge_id, as text, so a 64-bit hash stays exact), and the dashboard maps it to the row.
  4. The state stays live. For a page with a dashboard, the engine writes ["global-state", name] in the expressions (state: live). For a static style (export_style, a plain MapLibre app, RustGIS), it writes the start values (state: baked). Today the Rust engine always bakes them, so the Colour by menu, rsColor, the road fill switch and the Tunnels box do nothing on its style (dashboard_module.md).

When the dashboard needs the engine again

Some changes need new data or new expressions: a color column that the style does not have, a new ramp or range, width_by, another palette or profile, a level edit. The dashboard asks for them through a port, so that it does not depend on WebAssembly:

rsDashboard(map, {style, engine: {restyle: (change) => worker.restyle(change)}});  // returns a Promise of a StylePatch
  • Tiler.restyle(change) in roadstyle-wasm gives a StylePatch: the new paint and filter expressions of each layer role, the new roadstyle:color_options entry with its legend and, when the tiles must change, a new tile generation (rs://<generation>/..., as duckosm-rust's page does today with a new worker for each style). The worker keeps the roads table, so it computes the categories, the ramp and the legend from the column without a new read.
  • A color by a column is an expression on a property that is in the source (["get", column] in a match or an interpolate), so only the paint changes. For this, the column must be in the tiles (keep). Python bakes a color column for each option today (__rs_fill__<i>); the expression form is new behavior (decision 8).
  • The Python page has no engine. It shows only the options that it has in the style. can() returns false for a change that needs the engine, and the control does not show that choice. Nothing changes without a message.
  • duckosm-rust's page and the GeoLibre plugin attach the worker's restyle.

The rules:

  1. The merge is the merge of _settings.py today: the named profile over default, the named palette over amber, the palette over the profile, then each settings source in order (lowest first: ~/.config/roadstyle/roadstyle.json, ./roadstyle.json, $ROADSTYLE_CONFIG, use_settings, settings=). The old keys (_OLD_* tables) are read with a deprecation warning, as today.
  2. Validation after the merge. An unknown key is an error with its path and the nearest known key. Today an unknown key is ignored without a message.
  3. The file reading is an adapter. The core resolves from values (JSON text or Rust structs). The browser gives the files that it has. The bundled palettes and profiles are in the crate (made from the YAML files when the crate builds).
  4. The look has schema_version (an integer, starts at 1). The engine reads version N and N-1. A change that removes or renames a key increments the version.
  5. The JSON schema of the look is published with each release (look.schema.json). An editor can check a user file with it.
  6. One copy of the bundled files: src/roadstyle/data/ until phase 5. Then the files move into rust/roadstyle-look/data/, and Python reads the bundled values from the engine.

How

  1. Columns, not features. RoadTable keeps each property as one Arrow array, not a map per road. Text columns are dictionary arrays: one copy of each class name, color and road name. This is the open item of step 3 ("each text value is its own string").
  2. Geometry in one buffer. All coordinates are in one Vec<[f64; 2]> with an offset for each road (the GeoArrow layout). The coordinates stay f64, for parity with Python.
  3. No copy from Python. pyarrow gives the table through the Arrow C data interface (arrow::pyarrow). geopandas to_arrow() gives WKB, and the reader decodes it once.
  4. In the browser, one copy. The Parquet bytes go from duckdb-wasm into the module once. The worker keeps the tables, and the main thread gets only the style and the tiles.
  5. The tiled path makes no GeoJSON. The tile index reads the columns. Only export_inline writes GeoJSON, and it streams it source by source (as make_style does today).
  6. Typed metadata and slots. The base map, the slots and the layer list stop being serde_json::Value trees. The layer list stays JSON at the edge, when it is written.
  7. Caches. The resolved look is cached by its hash. The tiles are cached by (source, z, x, y) with a byte limit (LRU). No other cache before a measurement asks for it.
  8. Threads. Native only, feature parallel: the sources in parallel, the tiles in parallel. The solver stays single-thread (its stages depend on each other).
  9. The browser limits. A wasm32 module has at most 4 GB of memory, and a tab can get less. The module must stay under MAX_ROADS, and the error says to use a smaller area or the tiled path. The allocator grows the memory in large steps (16 to 256 MB), because each small step is slow in Edge on Windows.

Rules:

  1. One session for each lane. A lane edits only its own files.
  2. A change of the API of another crate is a small change of its own, reviewed first, and the other lane rebases on it.
