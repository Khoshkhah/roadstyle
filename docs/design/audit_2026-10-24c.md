## 2. The same four problems in both repositories

1. **Two copies of one pipeline.** duckosm-rust: the native build (`duckosm-build/src/lib.rs:200-400`) and the browser build (`duckosm-wasm/src/lib.rs:368-519`) are two copies that already differ (the browser ignores `infer_sidewalks`, the step timing and the mode summaries differ, OSM JSON input works only in the browser, one file-sink closure is copied 6 times). roadstyle: stage 2 has 5 entry points (`make_tiled`, `tiled_of`, `tile_made`, `tile_files`, `tile_files_with`), and the Python, wasm and CLI bindings each compose the stages again (`duckosm_plan` JSON, `LookCols`, `format()`, options parsing).
2. **Heavy dependencies pulled in by one small use.** duckosm-core depends on `roadstyle-rs` for 43 lines of levels code and gets arrow, parquet, yaml, sha2 and base64 (104 crates against 79). roadstyle's `cargo test` compiles bundled SQLite, `ring` (headless Chrome client) and `zstd`, and links every test with fat LTO, because `default-members` lists the CLI and the snapshot crate and the release profile has `lto = true`.
3. **No tests where the rewrites happen, and nothing measured.** roadstyle's engine has 2 unit tests; everything else is 33 end-to-end goldens plus the Python parity tests (only they cover `ColumnMap`, overlays, decks, palettes, pages, `export_look`, live state). duckosm-rust's CI never runs the `duckosm-build` tests (config, lane profile golden, levels golden) and never runs the wasm module it builds. Neither repository has a benchmark; the memory numbers in duckosm-rust's docs are from before levels, lanes, raw, bus and the ways tables existed.
4. **Big files with mixed responsibilities.** `layers.rs` (expressions + evaluator + road layers + base-map restyle), `simple.rs` (pieces + cuts + output + mitre), `network.rs` (junctions + split + merge + connect, one 316-line function), parquet `lib.rs` (five row-group helpers, the edge schema and the batch as two lists kept in step by hand).

### 3.2 New findings D1–D14

- **D1. Every `cargo test` builds C code, a Chromium client and fat LTO.** `Cargo.toml:7-8` `default-members` has `roadstyle-cli` and `roadstyle-snapshot`; `roadstyle-cli/Cargo.toml:11-13` turns on `gpkg` and always pulls the snapshot crate; `[profile.release] lto = true, codegen-units = 1` (`Cargo.toml:42-43`) and CI runs `cargo test --release`. 195 crates against 112. Fix: remove the two from `default-members` (CI builds them in their own job), make `snapshot` an optional CLI feature, move `lto`/`codegen-units` to a `[profile.dist]` for wheels and wasm. +8/−3 lines, low risk.
- **D2. duckosm-core links the whole facade for the levels.** `duckosm-core/Cargo.toml:21` → `roadstyle-rs`, used only in `levels.rs:8`. 98 crates against 49 for `roadstyle-levels` alone (17 after N26). Fix: depend on `roadstyle-levels`; make Arrow an optional feature of `roadstyle-model`; delete `roadstyle-rs` (213 lines; tests to `roadstyle/tests`, `main.rs` to `examples/bench.rs`). Touches both repositories (needs the owner's OK on the duckosm-rust side).
- **D3. The style is built 2 ways, and stage 2 makes 3 full copies of each inline source.** `sources.rs:159` clones the whole FeatureCollection to set `data`, then drops it; facade `tile_stage` `:114-122` writes each inline source to bytes and parses it back; `Sources::write_style` (`sources.rs:111`) is a second builder. This is the memory peak of stage 2 (Tartu buildings). Fix: copy the source object without `data`; one builder `style_with(|name, src| Inline | Url)` shared by `write_style`, `style`, `tile_stage` and N29. +10/−8 now.
- **D4. Colour parsing panics, 3 parsers with 3 rules.** `export_look.rs:19-21` slices `&s[1+2i..3+2i]` with no length check: `"#fff"` panics (a PanicException in Python, an abort in wasm; Python raises ValueError). `look/basemap.rs:95`, `look/ramp.rs:84-92` (byte length; a multibyte string panics). Two `mix` functions with different rounding (`export_look.rs:19` +0.5, `basemap.rs:191` `py_round`). Fix: one `roadstyle_look::color` module (`hex() -> Option<[u8;3]>`, `mix_half_up`). +15/−15.
- **D5. The engine has almost no tests of its own.** 2 unit tests (`colors.rs:316`, `features.rs:101`). Only the Python parity tests cover `ColumnMap`, `cap_col`, the boundary, overlays, items, metre widths, decks (`monaco_decks` data is Python-only), view palettes, pages and sidebars, `export_look`, live state, the `ev` evaluator. R7 and D14 rewrite exactly this code. Fix: add these cases to `make_goldens.py` as Rust goldens; unit tests for `ev`, `twin_pairs`, `mitre_ends`, `ColumnMap`. ~+300 test lines.
- **D6. Geometry helpers in 3–4 copies.** `length` (`model/geom.rs:227`, `levels/input.rs:426`, `tiles/lib.rs:458`); point-to-segment (`slots.rs:122`, `levels/input.rs:240`, `tiles/lib.rs:463`); along/interpolate/substring (`geom.rs:232`, `decks.rs:36,50`, `levels/input.rs:433,450`); `bbox` (`slots.rs:162`, `geom.rs:259`). Fix: extend `model::geom::line`, use it in the engine and tiles; levels after D2/N26. −60 lines; medium risk (float order can change goldens).
- **D7. The bindings repeat the composition code.** `duckosm_plan` JSON (py `lib.rs:430-444`, wasm `lib.rs:320-345`, keys differ), `LookCols` from an array (py `:377`, wasm `:197`), `format()` (py `:173`, wasm `:241`), options parsing in `page_from`, `makePage` and the CLI; stage 2 built 4 different ways. Fix with N21: facade `duckosm::plan(...) -> Plan`, `Format::parse`, `LookCols::from_slice`. −40 lines.
- **D8. Full-look leftovers after R5.** `contract.rs:93` `ROLES` has `shadows`, `casings`, `halves`, `ends`; `contract.rs:123,127` `roads-low-fill`/`roads-high-fill`; `layers.rs:854,877`; `engine/lib.rs:113` rejects `simple=false` only after the base-map and overlay work. Delete, with N16. −12 lines.
- **D9. Nothing is measured; the archive churns the tile cache.** No `benches/`, no `parallel` feature, no `examples/bench.rs` (plan items `rust_library.md:185,296,1136`). `Tiles::archive` (`tiles/lib.rs:251-275`) calls `tile()` per tile, each copies into the 64 MB cache and evicts. Fix: `bench.rs` with Monaco and Tartu numbers; `archive` uses an uncached builder; later rayon for the archive and XYZ walks.
- **D10. Piece properties built in full, then filtered.** `simple.rs:440-459` copies every mark as a `Value`, then `slim` drops most; `SimpleFeature::value` (`:538-545`) builds the whole `Props` per key read; `Get` returns a cloned `Value` (`props.rs:216,222`); `drop_empty_layers` (`layers.rs:507-516`) runs this for every feature of a layer nothing draws. Fix: pass the `read` set into `Piece::props`; `Get` reads one key and returns `Cell`. Measure first (D9).
- **D11. The road-table JSON writer builds a serde tree per row and per point** (facade `:338-341`). Fix: write with pyjson's number and string writers straight to `w`. +15/−10; byte parity is tested.
- **D12. The GeoJSON path of `tile_files_with` reads the road table as a JSON tree** (facade `:205-212`) while the Parquet path uses the typed `read_roads` (`:187`); wasm `FileSet` copies each file on each read (`roadstyle-wasm/src/lib.rs:422`). Fix: `read_roads` in both paths; borrow the files. −8.
- **D13. The levels version is set by hand and is wrong.** `ROADSTYLE_VERSION = "0.24.2"` (`roadstyle-levels/src/lib.rs:19`), crate 0.25.0; duckosm-rust writes it into `edge_levels_meta.roadstyle_version`. Fix: `env!("CARGO_PKG_VERSION")`. 1 line.
- **D14. Splits (moves only; with R7, after D5).** Functions over 80 lines: `layers.rs:576 road_layers` (389), `slots.rs:184 slots_source` (258), `decks.rs:121 bridge_decks` (171), `lib.rs:83 style_parts` (166), `layers.rs:996 restyle` (134), `simple.rs:698 mitre_ends` (131), `export_look.rs:25` (131), `levels/input.rs:492 relations` (157), `solve.rs:53` (143), `flow.rs:37` (140), `level_area.rs:49 make_area` (147), `page_options.rs:61 page_from` (121). Splits: `layers.rs` → `exprs.rs` (width/offset/metre curves), `eval.rs` (`py_truth`, `ev`, drop, swap, bake), `road_layers` in parts, base-map `restyle` to `overlays.rs` (it also shares its name with the palette `restyle` in `lib.rs:78`); `simple.rs` → pieces, cuts, output, `mitre.rs`; `overlays.rs` → base-map overlays and edge items; `tiles/lib.rs` → `clip.rs`, `mvt.rs`; `levels/input.rs` → geometry and relations; `level_editor.rs` → editor core and its CSV/JSON answers (N28).

Low value, noted: page option defaults in 3 places (`page_options.rs:17-21`, `index.js:25-41`, the Python signature; `popup_mode` differs); `live.js:10-48` repeats colour-by rules beside `colors.rs` (by design for live data); `Result<_, String>` grew from 158 to 164, the plan's error enums are not started.

### 3.3 roadstyle order

1. **N23** escape the data in the dashboard (~6 lines; a script injection from road names, in every page of both engines; open since audit 3).
2. **D1 + N17** slim the default build and the profiles; `serve` into the facade. Makes every later step faster to build and test (195 → 112 crates).
3. **N19 + D4** one WKB reader, one colour parser (two small input bugs; only io and look, no collision with other lanes).
4. **D3 then N29** one style builder, no deep copy, no write-then-parse (the stage-2 and page memory peak; the base for a typed stage 3).
5. **N21 + D7** one stage-2 API and the facade helpers the bindings share (3 entry points fewer; Python, JS and the CLI get the same two stages).
Then **D5** (Rust goldens for the parity-only paths) before **R7 + D14** (they rewrite `road_layers`), **D9** before **D10/D11/D12** (measure first), **D2** with duckosm-rust (needs the owner's OK), **D13** any time.

Edge memory.** Each `Edge` has two heap `Vec`s (refs, geometry; `model.rs:260-261`); a reverse edge clones both (`network.rs:427-435`); each mode clones the refs and 9 attribute strings per way (`filter.rs:560,577-587`). `Arc<[i64]>`/`Arc<[Pt]>` with a reverse flag would cut the edge heap a lot (edges add 881 MiB on Kentucky in wasm, design §7). Large cost; only if a larger area must fit in 4 GB.
- **U20. Errors and panics.** `Result<_, String>` is acceptable here; writer errors do not name the file (`build/lib.rs:117-141`, +3 lines). Panics reachable from input: `bus.rs:70` `w[0]` on a way with no nodes; `network.rs:381` `partial_cmp().unwrap()` on a NaN length. Low priority.

Not worth doing: merging duckosm-parquet and duckosm-duckdb (the small duckdb crate keeps the C++ build behind its feature); folding duckosm-build into core; error enums; removing arrow 58 (duckdb needs it).
