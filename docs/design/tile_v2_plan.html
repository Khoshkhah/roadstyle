Tiles v2: the review and the plan

Status: plan, 2026-10-27, for Kaveh's OK. No code. roadstyle branch design-tile-v2, from rust-engine at 7dbf59d. It includes phase 1 (design-tile-wk, not landed), an independent review and a web research. The same text: docs/design/tile_v2_plan.md.

The rule of this plan: a step is in it only if a measurement shows a real gain (time on the Burnaby tilted view, or a clear size), or if the data contract needs it. The other ideas are in Not done, and why.

Measurements: Burnaby, the tilted view (pitch 60, zoom 14), the page's tiles as static files, MapLibre 5.24.0 (the page's version), headless Chromium with software GL, the median of 5 runs, each on a new page, with a 200 ms start wait in each time. Two batches differ by up to 0.15 s.

1. The problem and the measured root

The page's tilted view of Burnaby takes 2.15 s from the jump to an idle map. MapLibre's parse and layout of the 30 tiles (5.9 MB, 115k features) is 1.41 s of it: that is the root.

Step of the 2.15 smsShare
The jump to the first tile request1005 %
tile() in the page's worker (28 calls)34616 %
The bytes to the main thread543 %
MapLibre's parse and layout1,41166 %
Draw until idle24211 %

The probes find two causes. Both are measured:

  1. MapLibre parses all the tiles on one worker. In 5.24.0 the default worker count is 1 (workerCount = isSafari ? min(cores, 3) : 1, in its source). 4 workers: −0.45 to −0.51 s. 6 workers: 827 ms; 8: 894 ms.
  2. The road layer's expressions. MapLibre calculates them for each feature. Phase 1 takes 0.3 s of it with 1 worker, and 0.08 s with 4.

What the review of the code found

  1. The engine (simple.rs) cuts each road into pieces and gives each piece a property map: the road's columns and up to 20 marks.
  2. The style builder (layers.rs) writes the look as expressions that read these marks. Phase 1 compiles the width and the offset into tables after the builder wrote them, with a fallback when the shape is not known.
  3. The tiles keep every __rs_* mark and the page's keys, not only the keys that the style reads. The pieces have no MVT id: promoteId reads __rs_edge. The encoder itself (interning, trees, cache, clip) is good.
  4. The page reads tile properties in filter.js, select.js, core.js and arrows.js. The popup, the panel and the live colours already use the road table (RoadTable, on the main thread) and the feature-state by row.
  5. Python has its own engine (still the default). Phase 1 had to be written two times.

3. The contract: tiles and data

  • A piece in a tile has the road's row as its MVT id, and only the keys that the style reads at that zoom. All pieces of a road share the row, so one feature-state paints the road.
  • The width and the offset are phase 1's tables (__rs_wk), written by the builder with no fallback.
  • The sort key is the small rank r, plus a raise for the top roads of rsColor (by ["id"]). The encoder writes a tile's features in the order (rank, row), so the order stays after a relevel.
  • The data stays on the main thread in RoadTable. The filters compute the rows that show and set one match on ["id"]; after a relevel they compute it again. Live colour, width and the glow stay feature-state by row.

Fixed and versioned

Fixed (a change is contract 3, with a migration): the row as the MVT id; only the keys that the style reads; the layout of the style keys (__rs_wk = a fixed mode of the kind and the flags × the versioned class list, __rs_k, r); the feature-state names rs_c, rs_w, hover, select; the source name roads; 512 px tiles. Versioned (from the look, no break): the value tables, the zoom spans, the palettes, the base-map layers. A second theme with the same class list uses the same archive. The style and the PMTiles metadata get contract: 2, a hash of the key layout and the generation.

5. The steps

Each step is one commit that passes CI and needs no raise. The picture stays the same (the Monaco and Tartu goldens, and the Burnaby view in the harness: 0 pixels differ). Phase 1 adds one key to each piece, so it comes after the steps that remove keys, and the ratchet runs after step 6.

pageStep 1: 4 MapLibre workers

What
maplibregl.setWorkerCount(Math.min(4, navigator.hardwareConcurrency || 1)) before the first map, in duckosm-rust's page and in roadstyle's page template. No tile change.
Why
MapLibre 5.24.0 parses all tiles on 1 worker by default [1], [2]. The 28 tiles of the view then wait for each other.
Gain
−0.45 to −0.51 s (1,343 to 889 ms; 1,402 to 892 ms). 6 workers: 827 ms; 8: 894 ms.
Risks
Each worker holds the tiles that it parses; a phone has fewer cores (the minimum with the cores).
Tests
The harness; the page's e2e tests and the phone check.
Page
A small PR of its own, now.

6. Future needs, checked

A planet service: an ID and a live colour for each road. The tile schema of a piece is the same in the page's live tiles, an xyz folder and a PMTiles archive. A planet archive is built one time; the live part is only feature-state. A planet build is a second driver over the same per-piece function (regions in parallel, written by tile). The row is valid in one generation (one build of the road set): the generation is in the tile URL and the metadata, and the archive and the live feed change together. duckOSM's edge_id is the stable public ID; the server keeps the map from edge_id to the row. The live service gives (generation, row, value) for the rows in a view, and the page sets rs_c and rs_w: no tile is made again. 152k states took 0.68 s one time, with no stall after it. Before the first planet build, count the planet's directed edges against 232 (D9).

Live changes with no new tiles. Colour, width, hover and selection are feature-state by row. A filter is one match on ["id"]. A relevel changes only the pieces of the changed roads and their ring; the rows stay, and the filters are computed again. A new road set is a new generation: a new tile prefix, and the page clears its state.

All consumers on one contract. The page and the editor (the wasm tiles), Python (the binding, D0), the static export (PMTiles or xyz, with a props file, D5) and roadstyle's HTML pages (inline GeoJSON: the same feature schema; the GeoJSON id is the row).

7. Not done, and why

  • One draw key for all style inputs; colour, opacity, dash, cap and filter as tables: no gain over phase 1 (1,221 and 1,204 ms against 1,196 ms).
  • A merge of the pieces of one road (research rank 3): 13 % fewer features; −0.10 s with 1 worker, −0.02 s with 4 (noise). Pieces with another sort rank (31 %) cannot merge: the draw order changes.
  • setSourceTileLodParams (research rank 4): (4, 3) and (2, 2) against the defaults (9.314, 3): the same 28 tiles and the same time.
  • Shared buckets (research rank 5): the road layer is one bucket; the 12 visible layers are 12 families, so nothing joins.
  • No data-driven sort key: −0.01 s; r stays for the raise of the top roads.
  • More than 4 workers: 6 gave 827 ms, 8 gave 894 ms: no clear gain, and a phone has fewer cores.
  • The data in a worker: no measurement shows a need; RoadTable on the main thread works.
  • A coarser simplification: 1 px gave 6.47 to 6.42 MB on Burnaby (about 1 %) and no time.
  • One casing per road at low zooms; one casing for two equal halves: not measured.
  • Class minzooms for steps, corridor, platform, bridleway, construction: −3 % features at z12; it changes the map.
  • A coarser grid at low zooms: geometry is 11 to 18 % of the bytes.
  • Colours as palette indexes: the text values of simple are 200 to 300 bytes in a tile.

9. The review

The independent review, finding by finding:

  1. Step 1 not measured: accepted; probed (above); the phase 1 step has no fallback.
  2. An archive tied to one look: accepted; the key layout is fixed, only the value tables come from the look.
  3. An id list wrong after a relevel: accepted; the filters are computed again after each relevel.
  4. A large match not measured: measured; 152k ids add 0.1 s to a filter change.
  5. The road table to a worker not measured: accepted; RoadTable stays on the main thread.
  6. r and the sort key can go: in part; __rs_s goes, r stays for the raise of the top roads.
  7. The id step too large: accepted; it is steps 4 and 5.
  8. Parts not defined: accepted; items keep __rs_pick; decks and shadows are inline GeoJSON and do not change; the contract test checks every zoom up to 24 for the tiles of the last zoom.
  9. Planet ids: accepted (D9).
  10. The order and the page's safety: accepted (step 8, D0).
