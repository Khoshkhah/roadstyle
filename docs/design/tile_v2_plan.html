Tiles v2: the review and the plan

Status: decided (Kaveh, 2026-10-27: D0, D1, D5 and D9 yes; phase 1 and D2 out). No code yet. roadstyle branch design-tile-v2, from rust-engine at 7dbf59d. Two reviews and a web research are applied. The same text: docs/design/tile_v2_plan.md.

The rule of this plan: a step is in it only if a measurement shows a real gain (time on the Burnaby tilted view above the batch noise of 0.15 s, or a clear size), or if the contract needs it. The other ideas are in Not done, and why.

Measurements: Burnaby, the tilted view (pitch 60, zoom 14), the page's tiles as static files, MapLibre 5.24.0 (the page's version), headless Chromium with software GL, the median of 5 runs, each on a new page, with a 200 ms start wait in each time. Two batches differ by up to 0.15 s.

1. The problem and the measured root

The page's tilted view of Burnaby takes 2.15 s from the jump to an idle map. MapLibre's parse and layout of the 30 tiles (5.9 MB, 115k features) is 1.41 s of it: that is the root.

Step of the 2.15 smsShare

MapLibre's parse and layout1,41166 %
Draw until idle24211 %

MapLibre parses all the tiles on one worker. In 5.24.0 the default worker count is 1 (workerCount = isSafari ? min(cores, 3) : 1, in its source). 4 workers: −0.45 to −0.51 s. That is the one large gain. With 4 workers, phase 1 gives −0.07 s, inside the batch noise, so it is not in the plan.

What the review of the code found

  1. The engine (simple.rs) cuts each road into pieces and gives each piece a property map: the road's columns and up to 20 marks.
  2. The tiles keep every __rs_* mark and the page's keys, not only the keys that are read. The pieces have no MVT id: promoteId reads __rs_edge. The encoder itself (interning, trees, cache, clip) is good.
  3. The colours are text in each piece (__rs_fill, __rs_casing, and one key for each colour option), so a tile set is tied to one palette.
  4. The page reads tile properties in filter.js, select.js, core.js and arrows.js. The popup, the panel and the live colours already use the road table (RoadTable) and the feature-state by row.
  5. Python has its own engine (still the default).

3. The design: tiles and data

  • MapLibre gets 4 workers: maplibregl.setWorkerCount(Math.min(4, navigator.hardwareConcurrency || 1)) before the first map.
  • A piece in a tile has the road's row as its MVT id, and only the keys of the contract: the keys that the style reads, and the three keys of the dashboard's filters (__rs_cls, lvl, __rs_access). The set is one for each tile layer (all zooms); the feature spans stay for each zoom (phase 0).
  • The sort key keeps the row: ["+", ["*", ["get", "r"], 4294967296], ["id"], ["case", ["in", ["id"], ["global-state", "rs_top"]], R, 0]]. r is the small rank; R lifts the top roads of rsColor. After a relevel the order is the same as on a new map. The row is under 232 (D9), so the key is exact.
  • No colour in a tile (the contract now; step 6 makes it): a class colour is ["at", ["get", "__rs_ci"], palette] in the style; a colour for each road is a number key or the feature-state rs_c. Then a second theme with the same class list uses the same tiles.
  • The data by row stays behind the RoadTable port (on the main thread, as now). The filters of class, level and access are filters on the tile keys; match on ["id"] is only for rsFilter and selections. Live colour, width and the glow stay feature-state by row (152k states: 0.68 s one time, and no stall after it).

5. The steps

Each step is one commit (or one page PR) that passes CI, lowers the budget and needs no raise. The picture stays the same (the Monaco and Tartu goldens, and the Burnaby view in the harness: 0 pixels differ). After step 5, phase 1 is measured again with 4 workers; it lands only if its gain is above the batch noise (0.15 s).

MapLibre 5.24.0 parses all tiles on 1 worker by default [1], [2]. The 28 tiles of the view wait for each other.

6. The server side

  • The generation of a road set is the first 16 hex characters of roadstyle_levels::edge_hash (the SHA-256 of the sorted edge ids): two processes that read the same roads give the same generation. The page, the tile URL, the PMTiles metadata and the live feed carry it. A row is valid in one generation only.
  • Tiles on a server: the eager path (add_lines) and Tiles behind an Arc: Tiles::tile(&self) with its cache behind a Mutex answers many requests at one time. LiveTiles (&mut self, the pieces made when a tile first shows them) is the browser's path.
  • Edits: replace_lines builds the layer's trees again and clears the whole tile cache for each edit. That is correct for the editor; its ceiling is frequent edits on a server, where an index of each road's features is the next step.
  • The data by row: the props file is in row order, cut into chunks by the tile grid at one zoom (one chunk today), behind the RoadTable port, so that a client loads only the chunks of its view. This is the contract; it is built when a server needs it.
  • Live colour for a planet: the server keeps the map from edge_id to the row; the live feed gives (generation, row, value) for the rows of a view, and the page sets rs_c and rs_w. No tile is made again. Before the first planet build, count the planet's directed edges against 232 (D9).

7. The contract: fixed and versioned

Fixed (a change is contract 3, with a migration): the row as the MVT id (a dense global row under 232, D9); only the contract's keys in a piece (the style's keys, and __rs_cls, lvl, __rs_access); no colour in a piece; the sort key of r and the row; the feature-state names (rs_c, rs_w, hover, select); the source name roads; 512 px tiles; the generation from edge_hash. Versioned (from the look, no break): the palettes and value tables in the style, the zoom spans, the base-map layers. The style's roadstyle:tiles and the PMTiles metadata get contract: 2 and the generation.

Shared ids. All pieces of a road share its row, so one feature-state paints the road. The MVT spec says an id SHOULD be unique in a layer; MapLibre accepts it (as with promoteId now). Other tools (QGIS, Martin's inspector, Tippecanoe) can merge or drop pieces with one id: the tiles are for MapLibre clients.

8. Not done, and why

  • Phase 1 (width and offset as tables): with 4 workers −0.07 s (889 to 815 ms), inside the batch noise; it adds a key to each piece and a table builder. Measure again after step 5.
  • One draw key; colour, opacity, dash, cap and filter as tables: no gain over phase 1 (1,221 and 1,204 ms against 1,196 ms).
  • A merge of the pieces of one road: 13 % fewer features; −0.02 s with 4 workers (noise).
  • setSourceTileLodParams: (4, 3) and (2, 2): the same 28 tiles, the same time.
  • Shared buckets: the 12 visible layers on the source are 12 families; nothing joins.
  • More than 4 workers: 6 gave 827 ms, 8 gave 894 ms: no clear gain, and a phone has fewer cores.
  • Filters by id list for class, level and access: +0.1 s for each switch with 152k ids, and they do not scale to a planet; filters on tile keys do.
  • A key set for each zoom: one set for each tile layer is simpler; the feature spans already act for each zoom.
  • The data in a worker: no measurement shows a need.
  • A coarser simplification: 1 px gave about 1 % on Burnaby and no time.
  • One casing per road at low zooms; one casing for two equal halves: not measured.
  • Class minzooms for steps, corridor, platform, bridleway, construction: −3 % features at z12; it changes the map.
  • A coarser grid at low zooms: geometry is 11 to 18 % of the bytes.

10. The reviews

The first review asked for the probes and the measurements that sections 1 and 8 now show; its findings are applied. The final review (Fable, approve with changes), finding by finding:

  1. Phase 1 and D2: cut; measure again after step 5.
  2. The sort key after a relevel: accepted; the key keeps the row (replace_lines adds new pieces at the end of the layer).
  3. The generation: accepted; the first 16 hex of edge_hash.
  4. The colour text in the tiles: accepted; no colour in a piece is in the contract now, and step 6 makes it.
  5. Filters by id list: accepted; __rs_cls, lvl, __rs_access stay; step 5 removes only __rs_edge2.
  6. Keys for each zoom: accepted; one set for each tile layer.
  7. Server concurrency: accepted (section 6).
  8. The data as an API: accepted; the props file by row in chunks, behind the RoadTable port.
  9. Step 1 on phones: accepted; the phone check measures the time.
  10. Shared ids: accepted (section 7).
